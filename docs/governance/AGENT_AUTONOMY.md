# NIN9ONE WORLD — AGENT AUTONOMY CHARTER

## Status

Founder-approved operating authority.

Effective: 2026-08-31.

## Purpose

NIN9ONE World may operate using bounded agent autonomy so routine implementation can continue without requiring the Founder to specify or supervise every reversible decision.

The Founder remains the final authority for canon, major creative direction, and high-impact decisions.

This charter operates alongside:

- [`WORLD_CANON.md`](WORLD_CANON.md), the authority for confirmed world meaning;
- [`WORLD_STATUS.md`](WORLD_STATUS.md), the authority for current execution state;
- [`AGENTS.md`](../../AGENTS.md), the contributor and pull-request rules.

If these authorities conflict, stop at the narrower authority boundary and surface the conflict.

## Operating Principle

The agent may determine:

> **How the established world is expressed.**

The agent may not independently determine:

> **What the world fundamentally means.**

Autonomy exists to increase execution velocity without silently expanding canon.

## Agent Authority

The agent may independently:

- inspect repository and governance truth;
- implement active tickets on feature branches;
- refactor existing systems when justified;
- improve maintainability and performance;
- run technical and visual validation;
- identify experiential weaknesses;
- determine the smallest useful next intervention;
- implement and evaluate reversible improvements;
- create and activate bounded follow-up tickets within delegated authority;
- sequence work based on observed results;
- maintain operational governance and architectural decisions;
- improve atmosphere, interaction, navigation, discovery, presentation, and sound;
- add non-canonical atmospheric details consistent with established canon;
- revise or abandon an ineffective approach.

Normal reversible implementation choices do not require Founder permission.

## Founder-Reserved Authority

The agent must not independently:

- create new canonical mythology or modify confirmed canon;
- alter the central self-discovery thesis;
- establish character origins or detailed biographies;
- resolve The Girl becoming Queen Nefera Sol;
- define Queen Nefera Sol's unresolved origin;
- define individual Wraiths or Wraith origins;
- establish Solari hierarchy or kingdom histories;
- create additional canonical worlds;
- introduce new foundational substances;
- canonize Living Filament;
- materially replace the established visual or material language;
- alter the Traveler → Seeker → Realization → Sovereign framework;
- publish externally;
- commit to significant paid infrastructure;
- fundamentally redefine NIN9ONE World.

Where canon is unresolved:

> **Preserve ambiguity rather than inventing certainty.**

## Experiential Progress Rule

Every autonomous implementation cycle should answer:

> **What can the player now see, feel, discover, understand, or do that they could not before?**

Prioritize perceptible player-facing improvement.

Technical infrastructure is allowed when it is genuinely required for a reasonably near-term experiential improvement. Infrastructure must not become the project.

Avoid:

- speculative architecture;
- unnecessary abstractions;
- premature content engines;
- procedural systems without immediate value;
- registries without an active experiential use;
- framework work justified only by hypothetical future scale;
- architecture work with no meaningful player-facing result.

## Autonomous Development Loop

```txt
Inspect current truth
        ↓
Experience the current build
        ↓
Identify the most important experiential weakness
        ↓
Choose the smallest meaningful intervention
        ↓
Implement
        ↓
Validate technically
        ↓
Experience visually
        ↓
Evaluate the result
        ↓
Document what was learned
        ↓
Continue / revise / escalate
```

Tickets are not mechanical checklists. Implementation should generate information that influences the next move.

## Ticket Authority

The agent may create and activate a follow-up ticket without Founder approval only when all of the following are true:

1. The work remains inside existing canon.
2. It continues an already-approved experiential direction.
3. It is reversible.
4. It does not create unnecessary foundational architecture.
5. It does not trigger a Founder-reserved decision.
6. It produces a tangible improvement to the experience.

Delegated work may include:

- discovery, interaction, camera, and navigation refinement;
- atmospheric responses and ambient audio;
- environmental polish;
- performance and accessibility improvements;
- visual feedback improvements;
- improvements revealed through actual use of The Citadel.

New worlds, new mythology, new civilizations, new foundational substances, and significant canon expansion require Founder approval.

## Canon Classification Rule

Any narrative content introduced through autonomous work must declare one of:

```txt
canonical
atmospheric
exploratory
```

### Canonical

May contain only meaning already supported by `WORLD_CANON.md` or separately approved by the Founder.

### Atmospheric

May reinforce established meaning through sensation, mystery, symbolism, environmental interpretation, or implication without creating new historical facts.

### Exploratory

May introduce deliberately unresolved signals but must not present them as confirmed truth.

Implementation does not make content canonical. Only Founder authorization may establish new canon.

## Resource and Usage Discipline

The operating goal is:

> **Maximum meaningful progress, not maximum agent activity.**

The agent should:

- reuse known repository context and documented decisions;
- batch repository inspection, testing, and visual evaluation where practical;
- avoid repeated full-repository scans without cause;
- avoid unnecessary repeated browser or screenshot passes;
- reuse evidence that remains valid;
- prefer deterministic local validation where appropriate;
- avoid excessive branching experiments and speculative work;
- keep one primary implementation direction active at a time;
- stop analysis when sufficient evidence exists to act.

## Autonomous Work Budget

The agent may perform a maximum of:

> **3 meaningful implementation tickets or major iterations between Founder reviews.**

This is a ceiling, not a quota.

A meaningful move should produce a material improvement or substantive learning. Minor fixes inside one coherent implementation must not be counted as separate moves.

> **You have three moves. Make them count.**

## Usage Escalation

Founder approval is not required for normal repository work, coding, local builds, testing, visual inspection, browser validation, or routine refactoring.

Escalate before committing to:

- unusually high compute usage;
- extensive repeated experimentation;
- significant paid services or third-party API consumption;
- infrastructure with ongoing cost;
- difficult-to-reverse architecture choices.

If resource use becomes disproportionate to likely player-facing value, stop and surface the issue.

## Founder Consultation Standard

Do not consult the Founder for ordinary reversible choices such as component naming, folder placement, minor spacing, normal refactoring, ordinary debugging, routine validation, low-risk responsive behavior, or small atmospheric adjustments.

Escalate only when:

- a Founder-reserved authority boundary is reached;
- materially different creative directions would substantially affect the experience;
- canon conflicts;
- the next meaningful improvement requires new world meaning;
- significant cost is required;
- a change is difficult to reverse;
- the established direction appears fundamentally unsuccessful.

## Escalation Format

When Founder input is genuinely required, provide:

### Decision required

One concise question.

### Why it matters

The creative, experiential, or governance consequence.

### Options

No more than three.

### Recommendation

A clear agent recommendation.

### If no decision is made

What can safely continue or what becomes blocked.

Do not manufacture Founder decisions merely to demonstrate consultation.

## Founder Review Rhythm

The default operating window is approximately 48 hours or up to three meaningful autonomous moves, whichever produces a useful review point first.

This is a review rhythm, not a literal timer. The agent may stop earlier when one strong move reveals that Founder input would materially improve the next direction.

Review triggers include:

- meaningful progress;
- three autonomous moves;
- a Founder-reserved decision;
- major learning;
- a significant proposed change in direction.

## Founder Review Format

At the end of an autonomous operating window, provide:

1. **What changed** — player-facing and material technical changes.
2. **What I learned** — what implementation and experience evaluation revealed.
3. **Current experience** — how The Citadel now feels and behaves.
4. **Repository state** — active ticket, completed work, branch/main state, validation, and known issues.
5. **Autonomous moves used** — each move identified against the three-move ceiling.
6. **Next autonomous direction** — what should happen next and why.
7. **Founder decisions** — no more than three; state `Founder decisions required: None.` when none are required.

The review should present something worth reacting to rather than merely list development activity.

## Anti-Patterns

Actively avoid:

- over-governance and unnecessary process documentation;
- infrastructure for hypothetical requirements;
- endless scene polish without deeper experience;
- lore quantity as a substitute for meaningful discovery;
- conventional game mechanics introduced by default;
- quest markers, achievement systems, collectibles, or unnecessary HUD;
- excessive exposition;
- premature procedural generation or world expansion;
- solving intentional mystery;
- complexity added merely because it is technically interesting;
- repeatedly asking the Founder to approve reversible choices.

The goal is not to build a game or an architecture demonstration.

The goal is to build a place.
